# CA_NERP 모바일 견적 UX 방향 및 1차 개선안

작성일: 2026-06-02

## 1. UX 핵심 원칙

모바일 견적은 웹 ERP 판매견적 화면의 축소판이 아니라, 현장에서 빠르게 견적을 작성하고 금액을 확인하는 전용 도구로 설계한다.

- 웹 기능 전체 복사를 금지한다. 웹의 그리드, 탭, 모달, 대량 처리 기능을 모바일 첫 화면에 그대로 옮기지 않는다.
- 모바일 현장 사용성을 우선한다. 한 손 조작, 짧은 입력 흐름, 빠른 재조회, 금액 확인을 기준으로 화면을 구성한다.
- 자주 쓰는 기능만 전면 노출한다. 샤시 작성/수정, 알유리 자동 생성 결과 확인, 총액 확인, 견적서 확인을 우선한다.
- 복잡한 기능은 `더보기` 또는 `고급기능`으로 숨긴다. 초기 화면에서는 사용 빈도와 현장 필요성이 낮은 기능을 노출하지 않는다.
- 샤시/알유리 흐름을 먼저 안정화한다. 이후 알유리 직접 입력, 몰딩, 도어 등 나머지 카테고리를 순차 확장한다.
- 모바일에서 수정 가능한 상태와 조회 전용 상태를 명확히 구분한다. 저장 버튼 비활성화만이 아니라 카드 진입, 상세 안내, 저장 guard까지 일관되게 처리해야 한다.

## 2. 현재 모바일 화면 평가

### EstimateList.vue

현재 장점:

- 견적 목록 진입점이 단순하다.
- 영업소 선택, 기간, 키워드 검색, 카드형 목록이 이미 모바일에 맞게 구성되어 있다.
- 목록 카드에 통합견적번호, 거래처, 현장, 등록일, 유효일이 표시된다.

불편할 수 있는 점:

- 검색 조건이 웹식 기간 조건과 제목 검색으로 나뉘어 있어 현장 사용자는 먼저 무엇을 입력해야 하는지 고민할 수 있다.
- placeholder는 `제목/현장 검색`이지만 실제 payload는 `searchItgEstiNm`만 전송한다. 현장명, 거래처, 견적번호까지 통합검색되는 것처럼 보이면 오해가 생긴다.
- 상태, 거래처, 현장, 견적번호를 빠르게 좁히는 UX가 부족하다.

모바일 UX 관점 개선 방향:

- 기본 검색은 통합검색 1개로 단순화한다.
- 기간, 상태, 영업소, 배송지점은 필터 버튼 안으로 이동한다.
- 최근 조회 조건, 최근 견적, 내 영업소 기본값을 활용해 첫 조회 시간을 줄인다.
- 검색 placeholder와 실제 검색 payload를 일치시킨다.

웹과 달라야 하는 점:

- 웹처럼 많은 검색조건과 그리드 도구를 항상 노출하지 않는다.
- 엑셀 내보내기, 그리드 설정, 대량 처리 기능은 목록 첫 화면에서 제외한다.

### EstimateNew.vue

현재 장점:

- 신규 견적 헤더 생성에 필요한 기본정보, 거래처, 현장, 인수/주문자, 비고가 분리되어 있다.
- 거래처 선택 후 담당자, 연락처, 할인등급을 보여주는 흐름이 있다.
- 영업소 선택값을 목록에서 이어받는 구조가 있어 반복 입력을 줄일 수 있다.

불편할 수 있는 점:

- 헤더 생성 화면에서 할인등급, 신용한도 등 많은 업무정보가 한 번에 노출되어 현장 입력 흐름이 길어질 수 있다.
- 필수 입력과 참고 정보의 시각적 우선순위가 더 명확해질 필요가 있다.
- 저장 후 바로 샤시 추가로 이어지는 동선이 더 직접적이면 좋다.

모바일 UX 관점 개선 방향:

- 필수값은 상단에 집중하고 참고 정보는 접기/보조 영역으로 둔다.
- 저장 성공 후 `샤시 추가`, `견적 상세로 이동`을 명확히 선택하게 한다.
- 거래처 검색 전 영업소 선택이 필요하다는 안내는 유지하되, 입력 흐름을 막는 메시지는 짧게 유지한다.

웹과 달라야 하는 점:

- 웹 QuoteHeader의 회계증빙, HCC상태, 복잡한 할인율 조정 기능을 모바일 헤더 생성 화면에 전면 배치하지 않는다.
- 모바일 헤더는 견적 생성에 필요한 최소 입력과 현장 확인 정보에 집중한다.

### EstimateDetail.vue

현재 장점:

- 헤더 요약과 샤시 견적 목록이 카드형으로 구성되어 모바일에서 읽기 쉽다.
- 샤시 카드에 모델, 순번, 상태, 사이즈, 수량, 틀짝망, 색상, VENT, 스크린, 핸들, 금액이 표시된다.
- 알유리 견적을 샤시 목록과 분리하려는 구조가 있다.
- 샤시 row는 수정 화면으로 이동하고, 알유리 row는 별도 표시하는 방향이 맞다.

불편할 수 있는 점:

- 총액 요약이 상세 상단에 충분히 강조되어 있지 않다.
- `+ 샤시`, `+ 도어`, `+ 유리`, `+ 몰딩` 버튼을 모두 노출하면 카테고리가 늘어날수록 복잡해진다.
- 준비되지 않은 카테고리 버튼이 많으면 실제 가능한 행동이 흐려진다.
- 알유리 자동 생성 항목이 왜 읽기전용인지 설명이 부족할 수 있다.

모바일 UX 관점 개선 방향:

- 헤더 요약 카드 아래에 총액 요약 카드를 둔다.
- 품목 추가는 `+ 품목 추가` 하나로 통합하고 액션시트/바텀시트에서 카테고리를 선택하게 한다.
- 초기에는 샤시만 활성화하거나 샤시/알유리 정도만 노출한다.
- 알유리는 별도 섹션과 `자동생성`, `읽기전용` 배지로 샤시와 명확히 구분한다.

웹과 달라야 하는 점:

- 웹 DetailEstimate처럼 모든 견적 카테고리와 그리드 편집 기능을 한 화면에 펼치지 않는다.
- 장바구니, 주문, 배분공장, 제조원가, 엑셀, 비교견적 등은 상세 첫 화면에서 제외한다.

### SashNew.vue

현재 장점:

- 샤시 입력이 기본정보, VENT/스크린/안전망, 핸들, 유리, 생산옵션, 비고, 금액으로 컴포넌트화되어 있다.
- 저장 후 닫기와 저장 후 계속 추가 흐름이 있다.
- 수정 진입 시 `selectSashDetail` 결과를 form으로 복원하는 구조가 있다.
- 금액 요약 표시가 있어 저장 후 계산 결과 확인이 가능하다.

불편할 수 있는 점:

- 옵션이 많아 모바일에서 스크롤이 길다.
- 생산옵션은 업무상 필요하지만 모든 사용자가 매번 수정하는 영역은 아니다.
- 저장 버튼과 금액이 화면 하단에서 멀어질 수 있다.
- 알유리 견적 옵션과 일반 유리 옵션의 관계가 처음 사용자에게는 혼동될 수 있다.

모바일 UX 관점 개선 방향:

- `기본정보`, `주요옵션`, `유리`는 기본 펼침으로 둔다.
- `생산옵션`은 기본 접힘으로 두고, 값이 들어간 경우에는 요약 배지를 표시한다.
- 금액 요약은 저장 버튼 근처 또는 하단 고정 영역에 반복 표시한다.
- 저장 버튼은 하단 고정이 적합하다.
- 알유리 견적은 샤시 저장 시 자동 생성될 수 있음을 유리 섹션 안에서 짧게 표시한다.

웹과 달라야 하는 점:

- 웹 SashForm의 모든 고급 옵션을 같은 밀도로 노출하지 않는다.
- 모바일은 자주 쓰는 옵션을 앞에 두고, 특수 옵션은 접힌 생산옵션 안으로 밀어야 한다.

## 3. 추천 모바일 견적 상세 화면 구조

견적상세는 다음 순서로 구성한다.

1. 헤더 요약 카드
   - 통합견적번호
   - 견적제목
   - 거래처
   - 현장
   - 상태
   - 유효일

2. 총액 요약 카드
   - 공급가
   - VAT
   - 합계
   - 카테고리별 금액 요약
   - 샤시/알유리/추후 카테고리별 금액을 한 줄로 요약

3. 품목 섹션
   - 샤시 견적
   - 알유리 견적
   - 추후 도어/몰딩/유통자재/패키지

4. 하단 또는 상단 액션
   - `+ 품목 추가`
   - `견적서 보기`
   - `더보기`

권장 배치:

- 상단: 제목, 뒤로, 상태
- 본문 상단: 헤더 요약, 총액 요약
- 본문 중단: 품목 추가 액션, 샤시 섹션, 알유리 섹션
- 하단: 견적서 보기, 더보기

## 4. 품목 추가 UX

현재처럼 `+ 샤시`, `+ 도어`, `+ 유리`, `+ 몰딩` 버튼을 모두 노출하면 모바일에서는 카테고리가 늘어날수록 복잡해진다.

추천 방향:

- 상세 화면에는 `+ 품목 추가` 하나만 노출한다.
- 클릭 시 액션시트 또는 바텀시트를 표시한다.
- 항목은 샤시, 알유리, 몰딩, 도어, 유통자재, 패키지 순으로 둔다.
- 초기에는 샤시만 활성화하거나 샤시/알유리 정도만 노출한다.
- 준비되지 않은 항목은 숨기는 것을 우선한다. 업무상 로드맵을 보여줄 필요가 있으면 `준비중` 배지로 표시한다.
- 수정 불가 상태에서는 `+ 품목 추가` 자체를 숨기거나 비활성화하고, 상태 안내만 표시한다.

품목 추가 바텀시트 예:

```text
[품목 추가]
샤시             사용 가능
알유리           준비중 또는 직접입력 가능 시 표시
몰딩             준비중
도어             준비중
유통자재         준비중
패키지           준비중
```

## 5. 샤시 카드 UX

샤시 카드에서 바로 보여야 할 정보:

- 모델명/창형
- 사이즈
- 수량
- 색상
- 틀짝망
- 상태
- 합계금액

보조로 보여줄 정보:

- VENT
- 스크린
- 핸들
- 주요 유리
- 비고 존재 여부

옵션 상세는 접기/펼치기 형태로 둔다.

- VENT
- 스크린
- 핸들
- 유리
- 생산옵션
- 비고

카드 동작:

- 편집 가능 상태: 카드 탭 시 샤시 수정 화면으로 이동한다.
- 수정 불가 상태: 카드 탭 시 조회 전용 화면 또는 안내를 표시한다.
- 알유리 row는 샤시 카드 목록에 섞지 않는다.

카드 표시 우선순위:

1. 모델명/창형, 상태, 순번
2. 사이즈, 수량, 색상, 틀짝망
3. 합계금액
4. VENT/스크린/핸들 요약
5. 접힌 상세 옵션

## 6. 알유리 카드 UX

알유리는 샤시와 혼동되지 않게 별도 표시한다.

방향:

- `알유리 견적` 섹션을 샤시 섹션과 분리한다.
- 카드에 `자동생성` 또는 `읽기전용` 배지를 표시한다.
- 샤시 저장 시 알유리 견적 옵션이 켜져 자동 생성된 항목임을 설명한다.
- 알유리 row는 샤시 수정 화면으로 이동하지 않는다.
- 나중에 직접 알유리 입력/수정 기능을 만들 경우 별도 알유리 화면으로 연결한다.

알유리 카드에서 우선 표시할 정보:

- 알유리 견적번호 또는 순번
- 품명/자재명
- 사이즈
- 수량
- 공급가/VAT/합계
- 생성 원천: 샤시 자동생성 또는 직접입력

알유리 직접 입력 기능이 생기기 전까지는 자동생성 row를 수정 대상으로 오해하지 않게 해야 한다.

## 7. 샤시 입력 화면 UX

SashNew.vue는 옵션이 많으므로 모바일에서는 섹션 우선순위와 접힘 정책이 중요하다.

추천 섹션:

1. 기본정보
   - 모형
   - 창형
   - 사이즈
   - 수량
   - 색상

2. 주요옵션
   - 틀짝망
   - VENT
   - 방충망
   - 핸들

3. 유리
   - SF/BF 유리
   - 알유리 견적
   - 유리부착
   - 실리콘마감

4. 생산옵션
   - 보강재
   - 밀링
   - 아파트
   - 특수옵션

5. 금액/저장
   - 공급가
   - VAT
   - 합계
   - 저장
   - 저장 후 계속 추가

UX 제안:

- 기본정보, 주요옵션, 유리는 기본 펼침으로 둔다.
- 생산옵션은 기본 접힘으로 둔다.
- 생산옵션에 값이 있으면 섹션 제목에 선택 개수 또는 요약 문구를 표시한다.
- 금액 요약은 하단 또는 저장 버튼 근처에 고정/반복 노출한다.
- 저장 버튼은 하단 고정을 권장한다.
- `저장 후 닫기`, `저장 후 계속 추가`는 유지한다.
- 수정 모드에서는 기존 옵션값이 기본값으로 덮이지 않는다는 신뢰가 중요하므로 변경된 옵션과 기존 유지 옵션을 명확히 분리한다.

## 8. 견적 목록 UX

웹처럼 검색조건을 전부 노출하지 않고 모바일식으로 정리한다.

추천:

- 기본 검색은 통합검색 1개로 둔다.
- 통합검색 대상은 견적제목, 거래처, 현장, 견적번호로 확장하는 방향을 검토한다.
- 필터 버튼 안에 고급조건을 넣는다.
  - 기간
  - 상태
  - 영업소
  - 배송지점
- 기본 기간은 최근 1일 또는 최근 7일 중 업무 사용 패턴에 맞춰 결정한다.
- 내 영업소 기본값과 최근 선택 영업소 저장은 유지한다.

현재 개선 후보:

- `EstimateList.vue` placeholder는 `제목/현장 검색`인데 payload는 `searchItgEstiNm`만 보낸다.
- 실제 백엔드가 제목만 검색한다면 placeholder를 `견적제목 검색`으로 좁혀야 한다.
- 백엔드를 통합검색으로 확장할 경우 payload 필드를 별도로 설계해야 한다.

## 9. 모바일에서 숨기거나 후순위로 둘 기능

초기 모바일 UX에서는 아래 기능을 전면 노출하지 않는다.

- 엑셀 내보내기
- 제조원가산출
- HCC견적복사
- 할인율설정
- 회계증빙서류
- 배분공장 적용/미지정적용
- 장바수량집계 원본/비교
- 그리드 설정
- 대량 일괄변경
- 복잡한 주문/배분 의뢰
- 웹 수준의 상세 그리드 편집
- 비교견적

처리 방향:

- 추후 필요하면 `더보기 > 고급기능`으로 이동한다.
- 모바일 구현 비용이 크고 사용 빈도가 낮은 기능은 웹 이동 안내로 처리한다.
- 주문/배분처럼 상태와 검증이 복잡한 기능은 샤시/알유리 저장 안정화 이후 별도 설계 문서를 작성한다.

## 11. 신규 카테고리 추가 순서 제안

### 1. 알유리 직접 추가/수정

왜 이 순서인지:

- 샤시 저장 시 자동 생성되는 알유리 흐름과 가장 가깝다.
- 이미 알유리 조회/표시 UX를 분리하는 방향이 잡혀 있다.
- 샤시 자동생성 알유리와 직접입력 알유리를 구분하는 기준을 먼저 세우면 이후 카테고리 확장이 쉬워진다.

예상 난이도: 중

모바일 UX 주의점:

- 자동생성 알유리와 직접입력 알유리를 배지로 구분해야 한다.
- 자동생성 row를 직접 수정할 수 있는지 정책을 먼저 정해야 한다.
- 샤시 재저장 시 자동생성 알유리가 갱신될 때 직접입력 알유리가 영향을 받지 않아야 한다.

웹 parity 문서 필요 여부: 필요

### 2. 몰딩

왜 이 순서인지:

- 샤시/알유리보다 입력 구조가 단순할 가능성이 높고, 현장 견적에서 함께 쓰일 수 있다.
- 모바일 카드와 간단 입력 폼으로 확장하기 좋다.

예상 난이도: 중

모바일 UX 주의점:

- 품목/규격/수량/단가 중심의 짧은 입력 흐름이 적합하다.
- 웹의 모든 그리드 기능을 가져오지 말고 자주 쓰는 입력만 먼저 선정해야 한다.

웹 parity 문서 필요 여부: 필요

### 3. 도어

왜 이 순서인지:

- 샤시 다음으로 업무 중요도가 높을 수 있으나 옵션과 검증이 몰딩보다 복잡할 가능성이 있다.
- 웹 DetailEstimate에 도어 흐름이 존재하므로 별도 분석이 필요하다.

예상 난이도: 중~상

모바일 UX 주의점:

- 도어 옵션을 샤시처럼 긴 폼으로 만들지 말고, 필수 옵션과 고급 옵션을 분리해야 한다.
- 도어 상태/주문 가능 조건을 모바일에서 어디까지 처리할지 정해야 한다.

웹 parity 문서 필요 여부: 필요

### 4. 도어기타/프리미엄도어

왜 이 순서인지:

- 도어 기본 흐름 이후에 확장하는 것이 안전하다.
- 특수 옵션과 가격 계산 조건이 별도로 있을 수 있다.

예상 난이도: 중~상

모바일 UX 주의점:

- 일반 도어와 다른 입력 항목을 별도 화면으로 둘지, 같은 도어 화면의 모드로 둘지 결정해야 한다.

웹 parity 문서 필요 여부: 필요

### 5. 유통자재

왜 이 순서인지:

- 품목 검색과 수량 입력 중심이면 모바일에 적합하지만, 자재 검색/재고/단가 정책 확인이 필요하다.

예상 난이도: 중

모바일 UX 주의점:

- 빠른 품목 검색과 최근 사용 품목이 중요하다.
- 바코드/품목코드 입력 가능성이 있으면 별도 UX 검토가 필요하다.

웹 parity 문서 필요 여부: 필요

### 6. 패키지

왜 이 순서인지:

- 여러 품목을 묶는 구조일 가능성이 있어 앞선 카테고리 안정화 이후가 적합하다.
- 모바일에서 패키지 구성/수정 UX가 복잡해질 수 있다.

예상 난이도: 상

모바일 UX 주의점:

- 구성품 확인, 수량 변경, 금액 요약을 작은 화면에서 명확히 보여야 한다.
- 패키지 내부 품목을 개별 수정할 수 있는지 정책이 필요하다.

웹 parity 문서 필요 여부: 필요

## 13. 구현 단계 제안

실제 구현은 이 문서 이후 별도 작업으로 진행한다.

### Phase 1: 견적 상세 핵심 UX 정리

- `EstimateDetail.vue` 총액 요약 카드 추가 설계
- 카테고리별 금액 요약 데이터 출처 확인
- `+ 품목 추가` 액션시트 구조 설계
- 샤시 카드 표시 필드 우선순위 정리
- 알유리 카드 `자동생성/읽기전용` 표시 정책 정리
- 수정 가능/조회 전용 상태별 액션 노출 정책 재확인

### Phase 2: 견적 목록 검색 UX 개선

- `EstimateList.vue` 통합검색/필터 UX 개선안 작성
- 현재 `searchItgEstiNm` 검색 범위 확인
- 견적제목, 거래처, 현장, 견적번호 통합검색 payload 설계
- 필터 바텀시트 또는 별도 필터 화면 설계

### Phase 3: 견적서/PDF 보기 조사 및 구현안 작성

- 웹 견적서 출력 API와 모바일 사용 가능 여부 조사
- 모바일에서 PDF 새 창/다운로드/뷰어 중 어떤 방식이 적합한지 결정
- 견적 상태별 견적서 보기 가능 여부 확인

### Phase 4: 알유리 직접 추가/수정 parity 문서 작성

- 웹 알유리 입력 화면과 저장 payload 분석
- 자동생성 알유리와 직접입력 알유리 구분 정책 정리
- 모바일 알유리 입력 필수 필드와 고급 옵션 분리
- 저장/수정/조회 테스트 시나리오 작성

### Phase 5: 몰딩/도어 확장 검토

- 몰딩 parity 문서 작성
- 도어 parity 문서 작성
- 각 카테고리별 모바일 최소 입력 필드 선정
- 상세 화면 품목 섹션 확장 방식 검증

## 결론

모바일 견적은 샤시/알유리 작성과 확인을 중심으로 작게 완성한 뒤, 카테고리를 순차 확장해야 한다. 웹 판매견적의 복잡한 기능은 모바일 첫 화면에 노출하지 않고, 현장에서 필요한 작성/수정/금액확인/견적서 보기만 전면에 둔다. 알유리는 샤시 자동생성 결과와 직접입력 대상을 명확히 분리해야 하며, 샤시 row와 같은 수정 화면으로 보내지 않는 정책을 유지한다.
